## 0.6.0. Удаление календаря без локального id

Сделано в расширении 0.6.0.

`clearLocalData` переносит в новое состояние только `googleCalendarId`. Снимок, mapping, журнал, тестовое событие, флаги цвета и настройки сбрасываются. Кнопка «Удалить календарь» после такой очистки остаётся активной и идёт в существующий `deleteCalendar`.

Поиск, если id уже потерян. Сообщение `findAppCalendars` и режим кнопки «Найти календарь расширения»:

- вызвать `listCalendars()` (`src/calendar/google-api.ts`); область `calendar.calendarlist` для этого уже есть;
- `ListedCalendar` включает `primary` и при необходимости `accessRole`; основной календарь (`primary === true`) в кандидаты не входит;
- кандидат, если `summary === CALENDAR_SUMMARY` («Расписание вуза») или `events.list` с `privateExtendedProperty=app=university-calendar-sync` вернул хотя бы одно событие этого приложения;
- переименованный календарь находится по служебному свойству событий, а не по названию;
- пустой календарь только с совпавшим названием показывается отдельно, с пометкой, что пар приложения нет;
- ноль кандидатов — сообщение «не найден», DELETE не отправляется;
- несколько кандидатов — список без автовыбора;
- удаление только id, который пользователь отметил, через текущий `deleteCalendar`, после `window.confirm` с названием;
- чужой календарь с тем же названием без явного выбора не удаляется и не записывается в `googleCalendarId` как рабочий календарь синхронизации.

После удаления состояние чистится: id, `testEvent`, `lessonMappings`, `syncJournal`, `lessonColorsReleased`. Настройки и `googleConnected` сохраняются. Отзыв OAuth не делается.

Тесты: очистка сохраняет id; поиск не вызывает DELETE; DELETE уходит только на выбранный id; primary отсутствует в списке; календарь без названия и без событий приложения отсутствует в списке.

## 0.7.0. Светлая, тёмная и тёмная рваная темы

Сделано в расширении 0.7.0.

Цели «тёмная тема», «рваный дизайн» и «переключатель трёх тем» — одна версия. Переключатель без третьей темы не выпускать. Третья тема использует палитру тёмной.

Данные. В настройки (`src/domain/types.ts`, `validateSettings`, `src/storage/state.ts`) добавить `theme: "light" | "dark" | "yellow"`. Пустое и неизвестное значение — `light`. Сохраняется вместе с остальными настройками.

Вид. В `src/ui/shared/app.css` уже есть переменные `:root`. Добавить `[data-theme="dark"]` и `[data-theme="yellow"]`. Применение: `document.documentElement.dataset.theme` из модуля рядом с UI, без `querySelector` (его запрещает `tests/gates.test.ts` вне парсера). На старте popup, review и options читают сохранённую тему до отрисовки содержимого.

- `light` — текущие цвета.
- `dark` — тёмный фон, светлый текст, те же карточки и таблица, без рваных краёв.
- `yellow` — цвета те же, что у `dark`. На `body.page` карточки с рваным краем (`clip-path`), лёгкий поворот и полоска скотча у заголовков. Таблица пар, поля и кнопки остаются ровными. `body.popup` (ширина 400px) эти эффекты отключает и остаётся плоским. Жёлтая палитра easytaxi не используется.

Переключатель — три radio в `src/ui/options/index.html`. Выбор хранится так же, как цвет календаря: в обработчике `change`, не через `querySelector`.

Тесты: settings принимает три значения и отвергает прочие; страницы содержат переключатель. Визуальную проверку трёх тем сделать в браузере на options, review и popup.

## 0.8.0. Доступ одногруппникам через Test users

Сделано. Публичный ключ записан в manifest, ID копий `dist` — `fgaajikioedkgeddlpfolngopnpkjegm`. Приватный `.pem` в репозиторий не входит. Рабочая сборка — 0.8.3. В 0.8.3 при открытии расширения сравнивается номер с последним выпуском указанного репозитория GitHub. Если выпуск новее, показывается кнопка «Скачать». Распакованную папку Chrome сам не подменяет.

Пароль, ежедневный код и постоянный код владельца в расширение не добавлять. Замок — только список Test users. Пароль в файлах расширения извлекается и копированию папки не мешает.

Поведение Google зафиксировано в README и коротко в настройках:

- почта добавляется и удаляется в Google Auth platform → Audience → Test users;
- пока статус Testing, чужой Gmail получает `access_denied`, даже с копией расширения;
- удаление почты не удаляет расширение с чужого компьютера и не удаляет календарь в его аккаунте; следующий вход или обновление токена отклоняется;
- токен Testing живёт около 7 дней, потолок списка — 100 почт;
- у каждого свой Google и свой календарь; токен владельца в storage не передаётся;
- чтение живой страницы остаётся на origin `https://stud.ibnd.ru` (`src/adapters/live.ts`, `canHandleIbnd`).

Стабильный id расширения. OAuth-клиент привязан к id расширения. В manifest поле `key` — только публичный ключ, который сохраняет этот id. Новый ключ, меняющий id, не генерировать: иначе клиент Google перестанет подходить, пока владелец не создаст новый. Приватный `.pem` в репозиторий не класть.

Раздача. Одногруппник получает zip каталога `dist`, не репозиторий. `oauth.public.json` остаётся в gitignore; client id уже попадает в `dist/manifest.json` при сборке и в документы не копируется.

В 0.8 приложение не переводить в Production, проверку Google не запускать, оплату не включать, новые scope не добавлять. Для будущего продукта путь такой: Production и проверка чувствительных scope календаря; список Test users тогда не является лицензией. Этот переход отдельным запросом, не частью 0.8.

## 0.9.0. Другие сайты вузов

`UniversityAdapter` описан в разделе 4 [spec.md](spec.md). Живой адаптер сейчас один: `src/adapters/ibnd/`. Второй сайт не подключать, пока в `tests/fixtures/` нет обезличенного HTML по списку раздела 7 [owner.md](owner.md). Селекторы не выдумывать. Неизвестный origin остаётся fail closed с понятным статусом, без записи в Google.

Пока образца нет, неизвестный адрес остаётся закрытым: расширение объясняет, что этот сайт ещё не подключён, и в календарь ничего не пишет.

План кода, когда образец есть:

- реестр адаптеров по origin рядом с `src/adapters/live.ts`; IBND остаётся в реестре;
- новый каталог `src/adapters/<site>/` с `extract` и `normalize`, своим `parserVersion` и своим `sourceKey`;
- `sourceKey` другого сайта не совпадает с `ibnd:schedule`, чтобы отмены одного источника не трогали события другого (фильтр отмен уже смотрит `sourceKey`);
- календарь приложения по-прежнему один;
- настройки могут хранить выбранный origin, но активная вкладка всё равно должна совпасть с адаптером, который умеет этот URL.

Идея других сайтов в [future.md](future.md) указывает на этот раздел. Пока версию 0.9 не попросили, новый парсер не писать.
